Invoice Finance Redesign Plan

The functionality is real and works end to end. The product does not yet look or feel like something a bank would buy. This is the plan to close that gap: what is wrong, the standard we are designing to, the screens, and the order of work.

Diagnosis in one line. We styled a component kit; we did not design a product. The seller app reads as a mobile layout stretched onto a laptop, the copy talks to developers, the data is thin, and session handling breaks after fifteen minutes. Colour was never the main problem.

2. The standard

Design to the level of the best B2B finance tools SMEs already use and trust — the Stripe dashboard, Wise Business, Mercury, Ramp. What they share is not a colour; it is a set of habits:

Restraint

White or near-white surfaces, one accent used for one purpose (the primary action and the active state), a grey scale with real hierarchy, hairline borders instead of shadows and tints. No gradients on functional surfaces.

Typography carries the brand

A single, excellent sans in 4–5 sizes with tight tracking on headings and tabular numerals on every figure. Money is always right-aligned and monospaced-figure. Labels are small caps in grey, never coloured.

Density with hierarchy

Tables with 44px rows, sticky headers, sortable columns, row hover, inline status; summary strips above tables; side panels for detail instead of full-page jumps. 12–16 data points visible at once on a laptop.

Documents are first-class

The invoice PDF is the hero of the detail page, rendered large, with extracted fields overlaid or listed beside it and low-confidence fields highlighted on the page itself.

Copy written by a product person

Every sentence in the user's words: "Your buyer hasn't confirmed yet — remind them" not "AWAITING_BUYER". No codes, flags or IDs. Errors say what happened and what to do.

States designed, not defaulted

Skeletons that match the layout; empty states that teach the first action with a sample; error states that recover inline; optimistic updates on accept/approve; toasts that confirm what changed.

3. Product structure

Three surfaces, one design system, one backend. The seller web app and the wallet show the same information architecture; the admin app is a workbench built for throughput.

3.1 Seller web app — desktop

3.2 Seller mobile and wallet

  • Same IA, re-flowed: KPIs become a two-line header (outstanding + next payment), the table becomes grouped rows (Needs you / In progress / Funded / Settled).
  • Upload is a two-step sheet: capture → "we're reading it" with the document thumbnail and fields appearing as they're read; no engine names, no word counts.
  • Offer acceptance is a full-screen confirmation with the three numbers and a slide-to-accept control; the receipt that follows is shareable.
  • Wallet: light theme by default, dark as an option, tokens shared with web so the screens are visibly the same product.

3.3 Admin workbench

  • Three-pane: queue list (left), case detail with the PDF and evidence (centre), decision panel (right) with approve/reject/adjust-terms and the policy explanation ("referred because seller has <6 months history; buyer tier B").
  • Keyboard-first: J/K to move, A to approve, R to reject — reviewers process dozens a day.
  • Portfolio page: exposure by buyer, concentration, ageing, dilution, a 90-day funded/settled chart; policy editor with diff and effective-date.
  • No internal IDs in cells; seller and buyer names link to profiles that show history, statements and limits.

4. Copy, states and trust

Copy rules

  • Status in words: "Offer ready — accept by Friday", "Waiting for buyer — reminded 2 days ago", "Funded — buyer pays 5 Dec".
  • Never show codes, flags, hashes or IDs unless the user asks ("View proof").
  • Money always with currency, thousands separators, two decimals in tables, none in headlines.
  • Errors: what happened + what to do + one button. No stack words.

States

  • Skeletons mirroring the final layout for every list and card.
  • Empty states that show a sample row and the single next action.
  • Inline recovery: expired session → silent refresh, then a one-line "signed you back in".
  • Optimistic accept/approve with undo for 5 seconds.

Trust signals

  • Document always visible; extracted values shown next to where they came from.
  • "Why this offer" expander: buyer tier, seller history, tenor — in sentences.
  • Public proof page redesigned as a certificate, not a checklist.

Demo mode

  • A small "Demo" tag in the header only. The OTP is auto-filled with no explanation text; the buyer-confirmation link appears as "Open the buyer's email" button. No configuration words anywhere.

5. Defects to fix regardless of design

  1. Session expiry. Implement refresh-token rotation in the seller web client (bff-gateway already issues refresh tokens) and retry the failed request.
  2. Developer text in UI. Remove the OTP explanation box, "Bearer token" error text, internal IDs in admin cells, engine names and word counts.
  3. Desktop layout. Replace the centred column with a top-nav + full-width layout; remove the sidebar for five items.
  4. Stripe band and hero gradient. Remove.
  5. Wallet dashboard shows "$128,430.50". Currency formatting bug, pre-existing.
  6. Admin queue columns clipped at 1440px. Rebuild as the workbench above.

6. How we work this time

  • Design first, in the browser. I build the design system and the five key screens as static, data-filled HTML mockups (seller overview, invoice detail, upload flow, admin workbench, mobile home) and show you screenshots at 390 / 1024 / 1440 in light and dark before any React or Flutter work. You approve or redirect at that point.
  • One system, three surfaces. Tokens live in one file consumed by web and exported to Flutter; no surface drifts.
  • Review gate. Nothing is called done until I have looked at every screen in every state at three widths and fixed what I see. You get the screenshot set with each delivery, not a URL to go find problems in.
  • Real data in demos. A seeded demo tenant with 14 invoices across every status, three buyers with history, and one invoice mid-pipeline, so no screen is ever empty.
